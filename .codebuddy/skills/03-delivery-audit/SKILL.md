# 题目 03 交付验收

## 用途

把《场景.doc》的过程要求与《题目.doc》的业务要求转成**可判定条目**，对指定提交版本做独立验收。默认立场：开发 Agent 的完成声明不构成证据。

## 触发场景

- 开发与测试完成后，PR 之前的整体自查。
- 教师/验收 Agent 判定"该题是否通过"。
- 缺陷修复后复验受影响条目。
- 提交班级群前的最终检查。

## 输入

1. 原始题面：`C:\Users\19513\Desktop\第3题\题目.doc`、`场景.doc`（必须读原文，不读摘要）。
2. 需求与规划：`deliverables/01-需求分析/`、`02-原型设计/`、`03-任务规划/`。
3. 被测版本：提交哈希、`dev/03` 分支、PR、主分支部署地址。
4. 证据目录：`deliverables/04~12`、测试与覆盖率原始文件、流水线运行记录。

缺失时标注"无法判定"，禁止用推测补齐。

## 执行步骤

1. 固定被测版本：记录分支、提交哈希、部署版本标识；三者不一致直接判阻断。
2. 按 `references/acceptance-checklist.md` 逐组检查：
   A 业务闭环（三组必演场景 + 异常）→ B 权限与数据隔离 → C 质量门禁（覆盖率/vet/race）→ D 过程证据（需求/原型/任务/AGENTS/Skill/会话）→ E Git 与 PR → F 自动部署与冒烟 → G 视频与群提交。
3. 每条给结论（通过/不通过/无法判定）+ 证据位置（文件:行、命令输出、运行标识、URL）。
4. 计算阻断数：任一阻断项存在即"整题不通过"，不得以"大部分完成"折算。
5. 输出缺口清单，按修复成本排序，标明复验时需要重跑的范围。

## 输出格式

```
# 题目 03 验收报告
被测版本：branch=dev/03 commit=<hash> deployed=<id> 时间=<t>
结论：通过 / 不通过（阻断 N 项）

| 分组 | 条目 | 结论 | 证据位置 | 缺口/备注 |
|------|------|------|----------|-----------|
| A | A-3 逾期分支可演示 | 通过 | 录屏 12:40，接口 409 见 test.log:88 | — |

## 阻断项
1. [D-2] 单元测试覆盖率 78%（核心包 submission 71%）→ 证据：coverage.out
## 无法判定项
## 复验范围
```

## 失败处理

- 证据缺失：判"无法判定"，写明缺哪份、应由谁在哪一步产出；不得默认通过。
- 证据自相矛盾（如报告说 90% 但 coverage.out 是 78%）：以原始文件为准，判不通过并记录矛盾点。
- 版本漂移（验收后改代码）：要求重新跑受影响门禁并重新验收，不得沿用旧报告。
- 发现造假迹象（编造编号、伪造流水线记录）：立即标记阻断并在报告中写明证据，不替其圆场。

## 完成标准

- A~G 七组全部有结论，每条有证据位置。
- 阻断项为 0；若有，明确列出修复责任与复验范围。
- 报告落盘到 `deliverables/06-Agent验收/`，并在 `调用记录.md` 登记调用时间、输入版本、结论摘要。
