## 2. 接口

`POST /api/assignments/{id}/reviews`（仅本班教师）

```json
{ "version_id": "SUB-...", "decision": "pass|reject", "feedback": "..." }
```

- 新建结论 `201`；重复提交同一结论 `200`（`replayed=true`，返回首次结论 ID）。
- 响应含 `state`（PASSED/RETURNED）、`current_version_no`、`decision`、`feedback`、`teacher_id`。
- 错误码：`forbidden_role` 403；`not_found` 404（作业/版本）；`not_published` 409；`stale_version` 409；`review_conflict` 409；`invalid_state` 409；`version_conflict` 409（DB 并发兜底）；`invalid_input` 400。

`GET /api/assignments/{id}/submissions` 的每个版本新增可选 `review` 字段；`state` 反映最终状态。

## 3. 事务与判定顺序

```
教师角色 → 作业同班/已发布 → 参数（version_id/decision/feedback）
        → 版本存在 → 状态行存在
        → 已有结论？（同 → 重放；异 → 409）
        → 是否当前版本？（否 → stale_version）
        → 状态是否 SUBMITTED？（否 → invalid_state）
        → 事务：INSERT review + 条件 UPDATE enrollments + INSERT event
```

- **"一版一结论"由 `UNIQUE(version_id)` 兜底**：并发两个不同结论同时到达，只有一个能插入；另一个在唯一约束处被拦下，服务层复查后返回 409 或重放。
- 状态推进用 `WHERE current_version_no = ? AND state = 'SUBMITTED'`，影响 0 行即 409，不存在"批阅成功但状态没动"。
- 批阅与提交在**同一把状态行锚点**上竞争：学生重交会推进 `current_version_no`，教师批旧版本必然失败（`stale_version`），这就是"批阅绑定版本"的实际效果。
- 批阅**不受截止时间限制**：教师可在截止后批阅，符合教学场景；该决定记入假设，未额外加校验。

## 5. 过程中发现并修正的问题

1. **权限矩阵用例过期**：`TestWriteEndpointRoleMatrix` 里"教师批阅"原本断言 501；D-07 落地后空请求体先返回 400。改为断言 400 并注明完整用例在 `reviews_test.go`，避免"旧断言假通过"。
2. **版本查询必须带作业范围**：最初只按 `version_id` 查提交，理论上可用别班版本编号试探批阅。改为 `WHERE id = ? AND assignment_id = ?`，并补 `TestGetSubmissionByVersionIDScopedByAssignment`。
3. **重放与 stale 的先后**：若先判"是否当前版本"，一次已成功的批阅在重试时会因学生已重交而变成 409，教师会误以为失败。改为先查已有结论（同结论重放），再判当前版本；理由写进代码注释与本记录。
