## 2. 请求契约的变化（对 D-05 的修订）

`POST /api/assignments/{id}/submissions`

```json
{ "content": "...", "request_id": "...", "base_version": 0 }
```

- `base_version` **必填**：首次提交传 0，更新时传客户端看到的当前版本号；缺失或为负 → 400 `invalid_input`。
- 响应：真正新建版本 `201`；幂等重放 `200`，body 中 `replayed=true`，`version_no` 为首次版本号。
- 错误码替换：D-05 的 `duplicate_request_id` 已删除，改为
  - 同内容重放：200（不再报错）
  - 异内容：409 `idempotency_conflict`（`details.existing_version_no`）
  - 版本落后/超前：409 `stale_version`（`details.base_version`、`details.current_version_no`）
  - DB 层乐观锁冲突且查不到同请求：409 `version_conflict`

## 3. 判定顺序（有意的设计）

```
角色 → 作业存在/同班/已发布 → 状态行存在 → 已通过 → 参数校验
     → 有效截止 → 幂等重放检查 → base_version 校验 → 落库（乐观锁）
```

- **重放检查放在 `base_version` 之前**：一次已经成功的请求，客户端重试时 `base_version` 必然"过时"，若先判 base 会把正常的网络重试误杀成 409，违背幂等目的。
- **`base_version` 在落库前**：旧页面请求不进入事务，`submit_version` 的插入、状态推进、事件写入都不会发生，因此"当前内容不变"是结构性保证，不是靠事后回滚。
- 并发落库失败后再按 `request_id` 复查一次：能查到且哈希一致 → 按重放返回，这是"同请求并发"能收敛到单版本的关键；查不到 → `version_conflict`。

## 5. 过程中发现并修正的问题

1. **D-05 的重复请求语义会误伤重试**：同 `request_id` 一律 409，导致网络抖动下的正常重试被当成冲突。D-06 改为"同内容重放 200、异内容 409"，并同步替换 D-05 用例 `TestSubmitDuplicateRequestID` 的断言。
2. **只判唯一约束不足以证明"不分叉"**：并发时两个不同 `request_id` 都基于 v0，先插入者成功，后插入者会先撞 `version_no` 唯一约束。补了 `TestConcurrentDifferentRequestsNoFork`，断言"恰好 1 个成功 + 最终只有 v1"，而不是只看返回码。
3. **重放不校验 `base_version` 是刻意的**，若按直觉把它放到最前面会导致重试失败；已在代码注释与本记录写明理由，避免后续"顺手优化"改坏。
