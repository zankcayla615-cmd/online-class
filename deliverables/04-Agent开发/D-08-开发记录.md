## 2. 接口增量

`POST /api/assignments/{id}/reviews` 响应新增：

```json
{ "points_awarded": true, "points": 10 }
```

- 首次通过：`points_awarded=true`、`points=10`。
- 重放（同版本同结论）：`points_awarded=false`、`points=0`。
- 退回：`points_awarded=false`、`points=0`。

分值与原因集中在 `store.PointsFirstPass=10`、`store.ReasonFirstPass="first_pass"`，服务层不写魔法数。

## 3. 一致性设计

```
BEGIN IMMEDIATE
  INSERT reviews (version_id UNIQUE)            ← 一版一结论
  UPDATE enrollments ... WHERE current_version_no=? AND state='SUBMITTED'
                                                ← 0 行 → ErrConflict，整体回滚
  INSERT events (type='reviewed')
  INSERT points_ledger (...) ON CONFLICT (assignment_id, student_id, reason) DO NOTHING
                                                ← RowsAffected=1 才是"本次真的发奖"
COMMIT
```

- **为什么用 `ON CONFLICT DO NOTHING` 而不是普通 INSERT**：普通 INSERT 撞唯一约束会让事务报错回滚，把"早就发过奖"变成 500/409，教师会以为批阅失败。现在冲突时事务照常提交，只是 `Awarded=false`。
- **为什么 `CreateReview` 返回结果结构而不是 `error`**：服务层需要知道"这次到底发没发"，若改成事务后再查一次，两次查询之间存在窗口（别的请求可能刚插入）。返回值来自同一个事务的 `RowsAffected`，语义准确。
- **"首次通过"如何界定**：唯一键是 `(assignment_id, student_id, reason)`，与版本无关。退回后重交再通过，仍是同一键 → 只发一次（符合"首次通过发奖"）。
- 题面未要求积分撤销/扣减，未实现；`points_ledger` 只追加。

## 5. 过程中发现并修正的问题

1. **`CreateReview` 只返回 `error` 时无法准确回答"是否发奖"**：改为返回 `CreateReviewResult{Awarded}`，把判断放在事务内（`RowsAffected`），避免"事务后再查一次"的竞态窗口。
2. **唯一约束不能当异常抛**：最初想靠 `IsUniqueViolation` 兜底，但那样会把"历史的已发奖数据"变成批阅失败。改为 `ON CONFLICT DO NOTHING`，并补 `TestAwardIsIdempotentWhenLedgerExists` 固化该语义。
3. **并发同结论批阅不是"一个成功四个失败"**：因为同结论走重放，5 个请求全部 200，但只有 1 个 `points_awarded=true`。用例按这个真实语义断言，避免以后误改成"多余请求报 409"。
