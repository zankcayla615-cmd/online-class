## 2. 代码与分层

```
internal/apperr/errors.go        结构化业务错误（Status/Code/Message/Details）
internal/service/assignment.go   业务规则：角色、长度校验、截止必须晚于业务时间、发布锁
internal/store/assignments_write.go  条件更新 + 发布事务 + 花名册落地
internal/httpapi/assignments_write.go  JSON 解析（拒绝未知字段）与错误映射
```

关键设计：

- **快照从表列复制**（`snapshot_* = title/requirement/deadline_at`），不是把请求参数写两遍，避免"快照与草稿不一致"。
- **并发正确性靠条件更新**：编辑与发布都用 `WHERE ... AND state='DRAFT'`，并发下只有一个成功，另一方得到 409，不存在"先查后写"的窗口。
- **发布即固化花名册**：同一事务内为班级学生建 `enrollments` 状态行（`INSERT OR IGNORE`），P02 只建 1 条、P01 建 5 条均有断言。
- **编号不依赖自增**：`HW-` + 8 位随机十六进制；随机源失败直接报错，不用系统时间兜底（业务时间必须来自注入时钟）。

## 4. 过程中发现并修正的问题

1. **测试用当前时刻直接比对**：`CreatedAt.Equal(clk.Now())` 因两次取时间不同而偶发失败。改为记录 `before/after` 区间断言，避免把"时间精度"当成 bug。
2. **冒烟脚本参数被空格切分**：`curl -d '{...}'` 在 PowerShell 下把 JSON 拆成多个参数，导致 400 与 307。改为请求体写文件 + `--data-binary @file`，脚本本身不是产品代码，但保留此经验在记录中。
3. 新增 `apperr` 包缺少测试导致覆盖率 0%，补 `errors_test.go` 至 100%。
